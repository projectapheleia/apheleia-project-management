# Changelog

## [Unreleased]

### Added
 - Format and themes in YAML. A `format_definitions` file in the input directory changes the page title, the heading above it, the line under it, the label of the theme chooser, the theme the report opens on and the logo in the banner. The logo can be an image file (`png`, `jpg`, `gif`, `webp` or `svg`) or SVG written in the YAML, which can use the colours of the current theme. Extra CSS can be added to every page.
 - Themes in YAML. A `themes_definitions` file adds themes to the chooser, each a set of CSS variables for the colours and fonts of the page, the colours of the charts, how the bars are coloured (as they are, a list of colours or a ramp) and extra CSS for that theme only. A theme gives only what differs and takes the rest from the `default` theme, or the one it `extends`. A theme with the name of a built-in theme replaces it, and `builtin_themes: false` offers only the themes the input gives.
 - The format and the three built-in themes are now the YAML files `format.yaml` and `themes.yaml`, and the logo the file `logo.png`, in the `defaults` directory of the package. The report is unchanged when no format or themes are given.
 - Invalid formats and themes are reported as errors, e.g. unexpected fields, an unknown default or extended theme, themes that extend each other, a missing logo file or values that would break the style sheet.
 - examples/format: `eighties`, neon and geometric with a new logo and two added themes, `noir`, with a silhouette logo and the built-in themes replaced by `Noir Light` and `Noir Dark`, and `errors` with one directory for each way a format or theme can be invalid. A new Format and Themes page of the documentation describes every setting.
 - Resources: availability periods. A resource can give a list of `periods`, each with a `start`, an `end` and an optional `availability`, the percentage of their time available from 0 to 100 (default 100). This covers leave, part time working, people joining or leaving and changes in hours. Time between periods is time the resource is not available. Only the first period can have no start and only the last can have no end. A resource with one period can still give `start` and `end` directly, now with an optional `availability`.
 - Resources: invalid periods are reported as errors. These are overlapping periods, an end before its start, an availability outside 0 to 100, a period other than the last with no end, `periods` mixed with a top level `start`, `end` or `availability`, an empty list of periods, unexpected fields and dates that cannot be read.
 - Resources: each period is a bar on the availability charts, faded in proportion to its availability, with the percentage shown on hover. A new Availability Periods table lists every period, and the resources table shows each resource's first start, last end and availability today. A resource with no period covering today shows `0% (no active period)`, to tell it apart from one on leave at 0%.
 - examples/resources: `availability`, a mix of resources that are and are not active today at a range of availabilities, and `errors` with one directory for each way periods can be invalid. The `simple` example now shows leave and part time periods.
 - examples/milestones: `windows`, and `errors` with one directory for each way a milestone can be invalid. An error case passes only if the report exits with a non-zero status and the expected `ERROR :` message; every other example fails unless the report exits with status 0.
 - examples/Makefile: `make report` prints `<example> : PASSED` or `FAILED` as each example finishes, then the number passed and failed, and supports `-j`. `make clean` prints a one line summary.
 - Milestones: a project can give a milestone a `start` and an `end` date instead of a single `date`. These milestones can overlap, and are drawn on the project timeline as a window: a dotted vertical line at each end joined by a horizontal line. Single date milestones are unchanged. In project tables the dates are combined, e.g. `2026-03-01 to 2026-04-30`; the table of projects using a milestone has separate start and end columns, with the start blank for a single date. A window milestone is due on its end date. A milestone with only one of `start` and `end`, a mixture of `date` and `start`/`end`, or an end before its start is reported as an error. The `milestones/windows` example shows both kinds.
 - Milestones: dates can be relative to another milestone of the same project, e.g. `end: "M1.start + 6 months"`, `start: "M1.end - 10 days"` or `end: "start + 7 weeks"`, in days, weeks, months or years. Milestones can refer to each other in any order; unknown milestones and loops are reported as errors.
 - Workpackages: optional `estimate`, a number and a unit written as e.g. `5 mm` (`md` man-days, `mw` man-weeks, `mm` man-months, `my` man-years, whitespace and case ignored; 5 man-days is a man-week, 20 man-days a man-month and 12 man-months a man-year). The effort allocated to the workpackage is checked against it: a workpackage allocated more than its estimate is marked `OVER ESTIMATE` with the amount over, in the workpackage tables and on its page, and listed under Workpackages Over Estimate on the project summary. Workpackages with no estimate are not checked. Invalid estimates (unknown unit, no unit, not a number, zero or negative) are reported as errors.
 - Workpackages: every table of workpackages has a Units select box (`my`, `mm`, `mw`, `md`) that shows the effort, estimate and allocated columns, and the messages in them, in that unit. Columns sort and filter on the value in the chosen unit, e.g. `> 100` with `md` chosen. The choice applies to every table on the page and is remembered by the browser.
 - Hover guidance for the `milestone range`, `milestone check`, `estimate check`, `check` and `problem` columns.
 - examples/workpackages: `estimates`, with no estimate, a generous, a low and an exact estimate, and `errors` with one directory for each way an estimate can be invalid.
 - Tasks: effort in the same units as workpackage estimates. The `estimate`, and `spent` and `remaining` in each status update, can be a number and a unit, e.g. `"3 mw"`, in `md`, `mw`, `mm` or `my`, and units can be mixed within a task. A plain number is in the new `task_unit` of the format, which is `md` by default, so existing task files are unchanged. `task_unit` applies to every task in the input.
 - Tasks: `resource` can be a list of names, for a task shared by several people. The effort is that of the task as a whole. A shared task is shown in full on the page of each of its resources, and the resource column links to each of them. Every resource of a task must now be defined in the resources.
 - Tasks: over estimate tasks are highlighted wherever tasks are shown. Every task table has an `estimate check` column marking a task `OVER ESTIMATE` with how far over it is, and whether the over-run is forecast, already spent or finished, and a Units select box. Tasks Over Estimate, worst first by percentage over, is shown on the tasks page and the Tasks tab of each workpackage and resource, as well as the project summary (where it was Tasks Past Estimate). The Task Progress Summary counts the tasks over estimate.
 - Tasks: invalid tasks are reported as errors: effort with an unknown unit, that is not a number or is negative, an estimate of zero, a status update with no date, spent or remaining, a date that cannot be read or two updates on the same date, an empty list of resources, a resource listed twice or not defined, and an unknown `task_unit`.
 - examples/tasks: `estimates` (good and bad estimates), `shared` (tasks shared by several people), `units` and `default_unit` (effort in every unit, and plain numbers in man-weeks), and `errors` with one directory for each way a task can be invalid.
 - Resources: over allocation. Each month a resource's allocations to every workpackage of every project are added up and compared with the time they have available that month, weighted by how much of the month each availability period covers. Months in which they are allocated more are listed in an Over Allocation table, consecutive months that are the same as one row, worst first, with `NOT AVAILABLE` for months they have no availability at all (before they start, after they leave). The table is on a new Allocation tab of the resources overview, the Allocations tab of each resource, and the project summary (for the project's resources).
 - Resources: an Allocation of Available Time heatmap on the resources overview, with a cell for each resource and month showing their allocation as a percentage of the time they have available, blue within it and red over it. The allocation charts on each resource's page have a dashed Available line, so over allocation shows as bars above it.
 - Workpackages: task effort. The effort spent plus remaining of a workpackage's tasks is checked against the effort allocated to it (`TASKS OVER ALLOCATION`), and the sum of their estimates against the workpackage estimate (`TASKS OVER ESTIMATE`), counting the tasks with no estimate. A Task Effort table is on the workpackages overview, the Workpackages tab of each project and the Tasks tab of each workpackage, and the workpackages that fail are listed under Workpackages Over Task Effort on the project summary.
 - Tasks: stale tasks. An unfinished task whose latest status update is more than `stale_days` (a new format setting, 14 by default, `null` to turn off) calendar days before the day the report is made is marked `STALE`. Every task table has an `update check` column, Stale Tasks is listed wherever Tasks Over Estimate is, and the Task Progress Summary and Task Status by Milestone count them. An invalid `stale_days` is reported as an error.
 - examples: `resources/over_allocation`, `workpackages/task_effort`, `tasks/stale`, `tasks/stale_off`, and `tasks/errors/stale_days_text` and `stale_days_zero`.
 - Report date. `apheleia_project_report --today YYYY-MM-DD` makes the report for that day, so the same plan gives the same report whatever day it is run. It is the day marked as today on the charts, the day unfinished tasks are forecast from if their latest update is older, and the day tasks are checked against for being stale, the current milestone found and availability shown. It defaults to the day the report is run. `--today None` makes a report with no date: nothing is marked as today, forecasts start from each task's latest status update, and the checks use the latest status update in the input, with the resources' available today column called available at latest update. A date that cannot be read is reported as an error. The report date is given on every page, through a new `{today}` in the `generated` line of the format.
 - examples: every example `Makefile` sets the report date to 2026-11-09 with a `TODAY` variable, so the examples no longer change with the day they are built. `today/none` is the `simple` example with no report date, and `today/errors/invalid_date` an invalid one.
 - Burncharts. Every project, workpackage and task page has a Burnchart tab with a burndown (effort remaining) and a burnup (effort spent against spent + remaining) of its tasks, and a Burn Summary of progress and the estimated end date. While work remains, the charts forecast it from the latest update (or today) at the rate the resources are allocated, an allocation of 1.0 doing one day of effort every working day, so the forecast follows each period of allocation. Each workpackage is forecast with its own allocation and a project adds up its workpackages; a task gets an equal share of its resources' allocation to its workpackage. Work left when the allocation runs out carries on at the average allocated rate and is marked beyond allocation. The estimated end is highlighted when it is beyond the allocation, or after the project end or the workpackage's milestone.

### Fixed
 - Clicking a bar to open its page stopped working on a chart once Plotly redrew it, for example the Resource Availability chart on the Resources tab of the main page when the tab was shown. Plotly throws away its event handlers whenever it redraws a chart, which also happened when a theme was applied. Chart links are now handled on the chart's own element, so they survive redraws, and dragging to zoom or pan no longer counts as a click.
 - Lines, markers and labels drawn in the text colour (the Available line on the allocation charts, the Estimate marker on Progress by Task and the totals on Resources Available Over Time) stayed dark on dark themes. They now take the theme's text colour.
 - An estimate such as `"3 hours"` or `"2 m"` was read as a time before it was checked, giving a confusing error. Estimates are no longer read as dates.
 - A task given a list of resources was counted once for each of them, multiplying its effort on the Task Progress chart.
 - The report failed if no task had a `description`.
 - Forecast finish dates truncated a fraction of a day of remaining effort. They now round it up.
 - The effort of a workpackage in the workpackage tables was the sum of its allocation fractions, ignoring the number of months. It is now allocation x months in person-months, as the allocation charts and resource pages already were.
 - Table column filters did not update the table until it was sorted. They now update as you type.
 - The workpackage tables showed the internal `outside` and `milestone date` columns used by the milestone check. They are no longer shown.
 - The chart colours of a non default theme were not applied on page load if the browser had already finished loading by the time the page script ran, so a saved theme could show charts in the default colours until it was chosen again.

### Changed
 - plotly is limited to versions below 8 (`plotly>=6.6.0,<8`), as the charts now set plotly properties directly, so a new major version is tried before it is allowed. The examples give the same charts with plotly 6.6.0 and 7.1.0.
 - Reports are made about twice as fast, e.g. the `construction_single` report in 9 s instead of 19 s, and look the same. Gantt, stacked bar and burn charts are built in one go from plain data rather than through plotly express and changes to plotly figures, the shading of the bars no longer copies plotly trace objects, and the progress of every task is worked out once rather than for each page.
 - Project, workpackage and task pages all start with Summary, Timeline and Burnchart tabs. The workpackage page's Timelines tab is now a Summary tab (description, milestone, estimate and task effort checks, task progress, and tasks over estimate or stale) and a Timeline tab (the workpackage and its tasks), and its Tasks tab keeps the progress of each task and the task table. The task page's Summary tab now shows the progress summary and latest status, with the timeline on its own Timeline tab. Its Progress tab, a weekly chart of effort spent and remaining, is removed: the burnup shows the same history with the forecast.
 - examples: the `construction_single` and `construction_multi` tasks start with a baseline status at the start of the project, and the `simple` tasks are updated through to November 2026, so their burncharts show the whole plan and progress to date.
 - The default logo is embedded at 414 x 132 rather than 1601 x 510, still three times the size it is shown at. Every page is about 80 KB smaller, e.g. the `construction_single` report drops from 16 MB to 10 MB.
 - Page colours that were fixed (the text on the banner, toolbar, table headings and badges, the logo background and the hover tips) are now variables of the theme, so a theme can change them. The three built-in themes look as they did.
 - Resources Available Over Time now counts full time equivalents, so a resource at 50% counts as 0.5 and one on leave for half a month counts as 0.5 for that month. Periods with no end now run to the end of the last bar, so the last bar is no longer under counted.
 - The Resource Availability chart no longer has a key, since each row is already labelled with the resource.
 - The Project Timeline help describes both kinds of milestone, a due date only and a window.
 - README: the examples table lists every example: `milestones`, `workpackages`, `tasks`, `resources` and `format` were missing.
 - Documentation: the resources and milestones input pages are rewritten in plain language, with worked examples, the rules, the report pages they affect and a table of the errors that are caught. The milestones page has a new timeline image showing both kinds of milestone, and the detail on milestone dates is now only on that page, with a short summary on the projects page.

## [v0.2.0] - 2026-11-07

### Added
 - Workpackages: optional `milestone`. The workpackage must end by the milestone date; starting early is fine. Workpackages that end after it, or whose milestone has no date in the project, are marked `OUTSIDE MILESTONE` in the workpackage tables and listed on the project summary. The milestone is marked with a diamond on the workpackage's bar in the workpackage timelines, and on the bars of its tasks in the task timelines. The `simple` example shows one workpackage within and one outside its milestone.

## [v0.1.0] - 2026-11-07

First release.

### Added
 - Input files: projects, milestones, resources, workpackages and tasks are described in YAML files, each with a `type` (`milestones_definitions`, `resources_definitions`, `projects_definitions`, `workpackages_definitions` or `tasks_definitions`) and a list of `data`. The input directory is searched recursively and all definitions of the same type are combined, so a plan can be one file per type or split by owner. Files with no `type` are ignored. Dates are written as `YYYY-MM-DD`, or `YYYY-MM` for the first of the month; `None`, `null`, `nan` and empty strings are treated as no date, and milestone names of the form `M<number>` are never mistaken for dates. Definitions with no name, duplicate names, unexpected (usually misspelt) fields and files that are not valid YAML are reported as a single `ERROR :` line naming the problem, with a non-zero exit status. Files with an unrecognised `type` are skipped with a warning. Any of the five types can be left out, so a plan can be built up a file at a time.
 - Milestones: named checkpoints defined once and given a date by each project that uses them, so projects can be compared like for like.
 - Resources: people and the period they are available. A resource with no end date is assumed available to the end of the charts.
 - Projects: start and end dates, description and a dated list of milestones, all optional beyond the project name.
 - Workpackages: areas of work within a project and the resources allocated to them, as a fraction of full time over whole months. Effort is reported in person-months, and a workpackage's start and end are taken from its allocations.
 - Tasks: individual pieces of work owned by a single resource, with a history of status updates recording effort spent and remaining in days. An optional `start` defaults to the project's previous milestone, and an optional `estimate` records the original effort in days; tasks whose spent plus remaining effort has grown past their estimate are listed on the project page, and in the Progress by Task chart each bar is split at the estimate, blue within it and red past it, and tasks with no estimate are flagged as missing. Status, percentage complete and a forecast end date are derived from the latest update; the forecast is the remaining effort in working days from the latest update, or from today if an unfinished task's latest update is in the past.
 - `apheleia_project_report`: generates the report from `--input` (default `.`) into `--html` (default `./html`). A top level index has tabs for projects, resources and milestones, and every project, workpackage, resource, task and milestone has an overview page and a page of its own.
 - Project summary: the status of the project's tasks grouped by the milestone they are needed for, and the tasks past their estimate.
 - Report: interactive [plotly](https://plotly.com/python/) charts - project, workpackage and task timelines with milestones and today marked, effort allocated by workpackage, project and resource, resource availability and the number of resources available over time, and task progress. Charts with a time axis can be viewed at monthly, quarterly or yearly scale. Every name in a table and every bar or segment in a chart links to the page for that item, and the same resource has the same colour on every chart. Charts and tables carry a help badge describing what they show.
 - examples/: `simple`, a minimal semiconductor project; `construction_single`, a multi-year construction project with one file per type; and `construction_multi`, the same project split into shared definitions and a tasks file per resource. `make report` and `make clean` in `examples/` build or remove every report, or in an example's own directory just that one.
 - doc/: Sphinx documentation covering installation, the input files, the report and the examples, illustrated with screenshots of the example reports, with an API reference generated by `doc/gen_all_rst.py`. Built with `make html` in `doc/`, and configured for [Read the Docs](https://readthedocs.org/) by `.readthedocs.yaml`. The documented version is read from `pyproject.toml`.
 - `setup.sh`: creates a virtual environment and installs the development build in editable mode, warning if Graphviz is not on PATH.
 - `__version__` is exported from the package, so `apheleia_project_management.__version__` works.
